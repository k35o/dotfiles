# Testing

テストは品質を上げる手段ではなく、品質が保たれていることを短い時間で確かめ、開発者に確信を与える手段。マージやデプロイの判断材料、リファクタリングの安全網、実行できる仕様書として役に立つものを書く。

## 進め方

- 振る舞いを決めたら先にテストを書き、Red、Green、Refactorを小さく回す。「あとで書く」テストは安全網と仕様書の役目を果たさない。
- すべてのコードに同じ密度で書かない。境界値、複雑な分岐、外部との境界、過去に壊れた所、仕様がよく変わる所に集中する。トリビアルなgetterやsetterには書かない。
- テストはスコープ（単体、統合、E2E）ではなくサイズで分類する。Smallは単一プロセスでメモリ内、Mediumは単一マシン内（DBやファイル可）、Largeは制約なし。Smallを多く、Largeを少なくする。

## 書き方

- 実装の詳細ではなく、利用者から見える振る舞いを検証する。内部stateや呼び出された回数を見ない。
- 期待値はリテラルで書く。テスト側でプロダクトコードと同じ計算をすると、同じバグを共有して通ってしまう（自作自演テスト）。

```tsx
// ❌ テスト側でも同じ計算をしている
const expected = (130 / (1 + 8 / 100)) * (8 / 100);
expect(item.taxAmount()).toBe(expected);

// ✅ 期待値はリテラル
expect(item.taxAmount()).toBe(9.629629629629629);
```

- 1つのテストで1つの振る舞いを検証し、テスト名でその振る舞いを表す。構成はArrange、Act、Assert。
- テスト同士の実行順に依存させない。結果が不安定なテストは見つけたらその場で直す。放置するとスイート全体が信用されなくなる。

## テストしにくいとき

テストが書きにくいのは設計の問題の兆候。外部API、現在時刻、ファイルシステム、DB、乱数への依存を境界に押し出し、コアのロジックを純粋に保つ（Humble Object）。

テストダブル（Mock、Stub、Fake）を使うか迷ったら [references/test-doubles.md](references/test-doubles.md) を読む。既定はFakeで、Mockは最小限にする。
