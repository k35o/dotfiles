# シークレット（fnox）

秘密は fnox 管理で、エージェントのシェルには常駐しない（対話シェル(個人機)では tier1 を起動時に自動ロード）。

- **tier1**（`[secrets]`: `SAKANA_API_KEY` など日常使う API キー）: `fnox exec -- <command>`。
- **tier2**（`[profiles.bot]`: GitHub App 秘密鍵 `K35O_BOT_*` など機密）: `fnox exec -P bot -- <command>`。

新しい秘密は「常駐させてよい API キー → `[secrets]`」「機密 → `[profiles.bot]` 等の profile」に振り分ける。

注意: `mcp__fnox__exec` は値が空のことがある（`[mcp] secrets=[]` / 起動時スナップショット）。確実なのは Bash CLI の `fnox exec`。

# 説明の置き場所

説明は種類ごとに置き場所を決め、同じ内容を重複させない。

- 処理のやり方はコード自体に語らせる。コードを読めば分かることを他の場所に繰り返さない。
- 保証したい振る舞い・仕様はテストコードで表現する。テスト名と構成を読めば何を約束しているか分かるようにする。
- 変更の背景・動機・判断の経緯はコミットメッセージに書く。コードに残らない文脈はここに残す。
- コードコメントには「なぜ素直な書き方をしなかったか」だけを書く（採用しなかった代替案とその理由、回避策が必要な事情、非自明な制約）。

コメントの書き方:

- デフォルトはコメント無し。自明な説明（`// ユーザーを取得` 等）やセクション区切り・装飾（`// ---- helpers ----` 等）は書かない。
- JSDoc/docstring は公開APIなど本当に必要なときだけ。
- 既存ファイルを編集するときは、その周辺のコメント密度に合わせる。
