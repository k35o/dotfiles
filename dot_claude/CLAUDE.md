# シークレット（fnox）

秘密は fnox 管理で、シェルには常駐しない。使うコマンドだけを `fnox exec` で包む。

- **tier1**（サービスごとの profile: `cloudflare` `vercel` `turso`）: `fnox exec -P <service> -- <command>`。
- **tier2**（`bot`: GitHub App 秘密鍵 `K35O_BOT_*`）: `fnox exec -P bot -- <command>`。復号のたびにユーザーのキーチェーン確認が要る。

新しい秘密は「CLI が日常的に使う API キー → そのサービスの profile（`--provider age`）」「機密 → `bot`（`--provider age-bot`）」に振り分ける。`fnox get` や `security find-generic-password` で値を直接読まない。

注意: `mcp__plugin_mcp_fnox__exec` は値が空のことがある（`[mcp] secrets=[]` / 起動時スナップショット）。確実なのは Bash CLI の `fnox exec`。

# 説明の置き場所

説明は種類ごとに置き場所を決め、同じ内容を重複させない。

- 処理のやり方はコード自体に語らせる。
- 保証したい振る舞い・仕様はテストコードで表現する。
- 変更の背景・動機・判断の経緯はコミットメッセージに書く。
- コードコメントには「なぜ素直な書き方をしなかったか」だけを書く。

# コミット・PR・Issueの言語

コミットメッセージや PR・Issue のタイトル・本文を書く前に、そのリポジトリの既存のコミットログや PR・Issue を確認し、日本語か英語かを多数派に合わせる。Renovate などの bot によるものは判断材料から除く。

# Desktop アプリに表示する文言

Claude Code Desktop のセッションの提案（`start_session` の title・prompt・background）やチャプター名（`mark_chapter`）は日本語で書く。ツール説明の例が英語でも、それに合わせない。

# 着手前の認識合わせ

実装・設計のタスクは、着手前に認識合わせの要否を判断する。依頼が曖昧・領域が不慣れ・影響が大きい場合は、先に grill-me スキル（インタビュー＋盲点列挙）を走らせてから作業に入る。

コードを書き始める前に、その領域のスキルが一覧にあれば先に起動する（React → react、テスト → testing、Web の UI/CSS → modern-web-guidance）。

# 設計・実装の原則

- 後方互換は守らない。互換レイヤー・フォールバック・移行コードを足すのではなく、古いパスを消す。
- 現在の要件を完全に満たす最小の実装を選ぶ。推測にもとづく抽象化・設定・間接層を作らない。
- システムは層で育てる。end-to-end で動く最小版から始め、動く製品の上に機能を積む。動く製品を未完成の複雑さと引き換えにしない。
- コンポーネントはモジュラーに保ち、関心を明確に分離する。
- 全体の複雑さを減らすか信頼性を上げるなら、実績があり保守されているライブラリを優先する。明確な理由なく一般的な機能を再実装しない。
- 自前実装やパッケージ追加の前に、プロジェクトに既にある依存を使い切る。ドキュメントと型を確認せずに「そのライブラリにはできない」と決めつけない。
- アーキテクチャの判断は長期を見据えて行う。「今だけ動けばよく、後で置き換える前提」の間に合わせを受け入れない。

# セキュリティレビュー

変更をレビューするとき（`/code-review`・`/security-review` を含む）は `~/.claude/claude-security-guidance.md` を読み、そのハードルールに反する箇所を必ず指摘する。

# 自動メモリ

自動メモリは使い捨ての観察層として扱う。永続化する価値が確認された学び（繰り返す失敗、確立した好み）は、dotfiles の CLAUDE.md やスキルへ昇格して git 管理に移す。
