# Systematic Debugging

症状を隠すのではなく、根本原因を特定してから直す。

推測で修正を重ねると、別の場所を壊したり、同じバグが形を変えて再発する。**原因を説明できるまで、修正コードを書かない。**

## 鉄則

- **根本原因を特定するまで修正しない**。「たぶんここ」で直さない
- **1度に1つの仮説だけ検証する**。複数箇所を同時にいじらない
- **3回直しても直らなければ、設計を疑う**。個別のパッチではなく構造の問題

## 4フェーズ

### 1. 再現

- エラーメッセージ・スタックトレースを**最後まで読む**。要約で判断しない
- 確実に再現する最小手順を見つける。再現しないバグは直せない
- flakyなら、再現率・タイミング・環境差（並行実行、時刻、乱数、キャッシュ）を記録する

### 2. 切り分け

- 直近の変更を疑う: `git log`・直近のdiff・`git bisect` で「動いていた地点」との差分を取る
- 問題の範囲を二分探索で狭める。入力・レイヤー・依存を1つずつ外して切り分ける
- 「どこまでは正しいか」を確定させ、故障点を1箇所に追い込む

### 3. 根本原因

- **1つの具体的な仮説**を立てる（「Xの条件でYがnullになる」）。曖昧な「なんか変」で止めない
- ログ・デバッガ・最小の再現コードで仮説を検証する。当てずっぽうに print を撒かない
- 症状（NPE、500、白画面）ではなく、**それを引き起こした原因**まで遡る

### 4. 検証

- まず**バグを捉える失敗するテスト**を書く（[testing](../testing/SKILL.md) の Red）
- そのテストを通す**最小の修正**を入れる。ついでのリファクタや無関係な変更を混ぜない
- テストがGreenになり、再現手順で症状が消えたことを実際に確認する
- 同じ原因が他の箇所にもないか横展開して確認する

## 適用の判断

### 使うべきとき

- 原因が自明でないバグ、再現条件が不明なバグ
- 一度直したのに再発する、直したら別が壊れる
- flakyなテスト、CIだけで落ちる

### 不要なとき

- 原因が一目で分かるタイポや明白な誤り
- エラーメッセージが直接原因を示している軽微な修正

## 関連

- 根本原因の特定が難航したら [codex-reviewer](../codex-reviewer/SKILL.md) で外部視点を入れる
- 検証は [testing](../testing/SKILL.md) の失敗するテスト先行で固定する
- 完了報告の前に [verify-before-done](../verify-before-done/SKILL.md) で実際に直ったことを確認する
