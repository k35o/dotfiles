# 文章を書く

日本語の文章を書く、書き直すときの判断基準。表記と語句のルールは`writing-review`と共通の参照ファイルを使う。

- 書き始める前に読む：[../writing-review/references/ai-slop.md](../writing-review/references/ai-slop.md)（AI Slop、比喩動詞、擬人化）
- 表記ゆれや言い回しに迷ったときに読む：[../writing-review/references/japanese-rules.md](../writing-review/references/japanese-rules.md)
- 表記の慣習（英日スペースなし、半角英数字、中黒で並列しない、`用語：説明`）は`writing-review`の「観点3: 表記の慣習」に従う

## 共通の方針

- 予告せず、具体的な文から入る。「この記事では〜を紹介します」「重要なのは〜」のような前置きは書かず、その中身を書く。
- 一文は45字を目安にする。読点は3つまで。60字を超えたら、主語と述語が離れていないかを見て分ける。
- 文体はですます調。例外は下の用途別に書く。
- 書き直すときは意味を変えない。原文にない理由や数値、感情、主語を足さない。決まらない箇所は残し、確認したい点として添える。
- 強調は文の組み立てで行う。太字や絵文字、ラベル型リスト（`**ラベル**: 説明`）に頼らない。

例（一文の長さ）:

- NG: `startViewTransition`は`Document`オブジェクトのメソッドとして実装されており、呼び出しに応じて`ViewTransition`オブジェクトを返します。
- OK: `startViewTransition`は`Document`のメソッドです。呼び出すと`ViewTransition`オブジェクトを返します。

## 用途別

### ブログ記事

- 「はじめに」の最初の文で、題材が何で何ができるのかを言い切る。
  - NG: この記事では、View Transition APIについて紹介します。
  - OK: View Transition APIは、UIの遷移にアニメーションを付けるAPIです。Baseline 2025に入りました。
- 公式ドキュメントの要約で終わらせず、自分で動かした結果や落とし穴、使い分けを1つ以上入れる。
- k8oリポジトリの記事は`blog-review`の規約に従う（本文で太字と表を使わない、見出しは`##`から）。

### スライド

- 見出しは体言止め、本文は短い文で書く。
  - 見出し: 同一オリジンの遷移
  - 本文: `@view-transition`を両方のページで有効にします。
- 1枚に言いたいことは1つ。説明しきれないことはスライドに詰めず、話す内容に回す。

### 仕事の文面（Slackとメール）

- 用件から書く。クッション言葉と前置きは削る。
  - NG: お疲れ様です。先日の件について確認させていただきたく、ご連絡いたしました。
  - OK: 先日の件で確認させてください。〇〇は△△の想定で合っていますか？
- 相手にしてほしいこと（確認、判断、期限）を1文で明示する。
- メールは冒頭と結びの定型を1行ずつだけ置き、本文はSlackと同じく簡潔に書く。

### PR本文

- ですます調で書く（例: スクロール位置を復元する処理を追加しました。）。
- 構成と書く範囲は`CLAUDE.md`の「コミットとPR」に従う。

### コードコメント

- 日本語の常体で書く（例: `// 初回描画では遷移アニメーションを付けない`）。
- 周りのコメントや識別子が英語のファイルやリポジトリでは英語で書く。

## 仕上げ

書き終えたら、次を実行して(3)英日スペース、(5)読点、(6)連続漢字、(7)文体混在の出力を直す。

```bash
bash ${CLAUDE_SKILL_DIR}/../writing-review/scripts/check.sh <file>
```

公開前の通しレビューが要るときは`writing-review`を使う。

## 指摘を受けたら

このスキルで書いた文章に指摘を受けたら、直したあとで、別の題材でも同じ指摘を受けそうかを判断する。受けそうなら、下のGotchaか用途別の項目に足す一文を変更案として示し、合意してから反映する。レビューでも検出したい語句や表記なら`writing-review`の`references/`に足す。題材や事実だけに関わる指摘は取り入れず、その理由を一言添える。

反映はdotfilesの`dot_agents/skills/`でブランチを切り、PRを立てる（`skill-creator`のGotcha参照）。

## Gotcha

- 既存のブログ記事を手本に読むと、「この記事では〜を紹介します」の予告文と、中央値55字の長めの文をそのまま真似てしまう。手本にするのは語彙と表記だけにする。
- Web機能の記事では、Baselineでそろっている値や機能だけを書く。仕様の値を一覧にすると、一部のブラウザだけが対応する値まで紹介してしまう。
- 仕様の訳語（「表意文字」など）を本文にそのまま使わない。読者に通じる語（「漢字やかな」）に言い換え、仕様での呼び名は必要なら一度だけ添える。
- 語を並べるときに中黒（・）を使いがち。「、」や「と」でつなぐ。
