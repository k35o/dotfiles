# PR

ローカルの変更からPRのオープンまでを進める。

## Gotcha

- 会話中に参考として出てきた外部リポジトリのIssueやPRのURL、`owner/repo#123`をPRのタイトルと本文に書かない。GitHubが相手のリポジトリに被リンクを残してしまう。リンクするのは作業中のリポジトリのものだけで、どうしても外部に触れるときはバッククォートで囲んでオートリンクを止める。
- 本文に実装途中の方針変更や試行錯誤の過程を書かない。最終的な状態だけを書く。
- mainに直接プッシュしない。

## 進め方

1. ブランチを切る。名前は`feature/`、`fix/`、`chore/`に説明を続ける。すでに作業用のブランチにいればそのまま使う。
2. commit-creatorスキルでコミットする。デバッグコードや一時ファイルが入っていないか確かめる。
3. `git push -u origin <branch>`でプッシュする。
4. 同じ変更のPRがすでに無いか、ターゲットブランチ（通常はmain）が正しいかを確かめる。
5. 本文を書き、`gh pr create --title "<title>" --body "<body>"`で開いて`gh pr view --web`で見せる。タイトルは短くし、詳細は本文に書く。

## 本文

変更の規模に合わせて詳しさを変える。

小さな変更（ドキュメントの更新、1ファイルの修正など）は、何をしたかとなぜしたかを2〜4文で書く。

大きな変更（新機能、複数のコンポーネントにまたがる変更など）は次の見出しで書く。テストと関連Issueは該当するときだけ書く。

```markdown
## 概要

## 動機

## 詳細

## 気をつけるポイント

## 影響範囲

## テスト

## 関連Issue
```

気をつけるポイントには、レビュアーに見てほしい箇所と既存の挙動への影響を書く。テストには実際に確かめたことだけを書く。
