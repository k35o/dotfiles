# 文章レビュー

日本語の技術文書の文章品質をレビューし、重要度つきの指摘レポートを出す。媒体を問わない汎用版で、プロジェクト固有のレビュースキル（ブログMDX用の`/blog-review`など）があれば媒体固有の点検はそちらに任せ、ここでは文章面だけを見る。

文章を書く、書き直すときは`/writing`を使う。`references/`の2ファイルは`/writing`と共通なので、片方だけに合わせて書き換えない。

ファイルは変更しない。修正を頼まれても、先にレポートを出し、どの指摘を直すか合意してから着手する。コードの動作や技術的な正しさは対象外で、レポートに「別途確認」と一言添える。

## 進め方

1. 対象を通しで一度読む。
2. 機械的補助コマンドで、数えれば判定できる項目を先に洗い出す。
3. 観点1〜7を判定する。観点4〜6は通し読みのあとに見る。
4. 重要度（要修正、推奨、任意）を付けてレポートにまとめる。

## 機械的補助コマンド

```bash
bash ${CLAUDE_SKILL_DIR}/scripts/check.sh path/to/doc.md
```

出力は番号つきの節に分かれる。(1)太字、(2)ラベル型リスト、(3)英日スペース、(4)全角英数とダッシュと中黒、(5)読点4つ以上、(6)連続漢字7字以上、(7)文体混在の手がかり。(1)〜(4)はコード内も拾うので、マッチがコードフェンスやインラインコードの中なら違反にしない。(5)(6)はそのまま要修正の候補、(7)は両方が1以上なら該当文を目視で確かめる。

## 観点

### 観点1: 日本語の文章ルール

文体統一、文末句点、読点数、連続漢字、ら抜き、冗長表現、ひらがな化、表記ゆれ、誤用など。全ルールとNG→OK例は、観点1を判定するときに [references/japanese-rules.md](references/japanese-rules.md) を読む。

### 観点2: AI Slop、LLMっぽい言い回し

一文単体で判定できる語句レベルの定型表現を見る。中身のない太字、ラベル型リスト、誇張表現、「重要なのは〜である」式の予告、空虚な形容や動詞、比喩動詞、擬人化、直訳調など。一覧とNG→OK例は、観点2を判定するときに [references/ai-slop.md](references/ai-slop.md) を読む。

一般の文書では、強調や初出用語など要所の太字は使ってよい。弾くのはAI的な機械的な太字だけで、媒体が太字なしの方針ならそれに従う。

### 観点3: 表記の慣習

| 観点             | 内容                                                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 英日スペース     | 英語（英数字）と日本語の間にスペースを入れない。`React のフック`ではなく`Reactのフック`                                |
| 半角/全角        | 数字、英字、記号は半角に統一する                                                                                       |
| ダッシュ、中黒   | emダッシュや`──`を地の文と見出しで使わない。日本語の語の並列に中黒を使わず、「、」「と」でつなぐ（固有名詞の内部は可） |
| 用語の定義       | 用語と説明は全角コロンで書く（`用語：説明`）                                                                           |
| インラインコード | API名、プロパティ名、コード断片はバッククォートで囲む                                                                  |

### 観点4: 整合性と流れ

通しで読み、段落、節、文書全体で論理が破綻していないかを見る。読者が実際につまずく箇所に絞る。

- 論理の飛躍や矛盾、接続詞と論理関係のずれ、定義前の用語使用、説明の順序（前提→本論→応用）
- 重複：理解を進める繰り返しなら任意、同じ理解を二度させるなら推奨
- 見出し：節が答える問いや扱う対象を表す単一の句か。情報量ゼロや、結論を言い切るオチになっていないか（「はじめに」「おわりに」など慣例の見出しは許容）
- 主述のねじれと指示語：読点3つ以内でも、引用、条件、結論を1文に詰めて60〜80字を超え、主語と述語が遠いものは分割を提案する
- 論証の厳密さ：推量を根拠なく断定にしていないか、別々の原因を「同じ」とまとめていないか、因果に機構を示しているか、確認していないことを確認したように書いていないか
- 回収：冒頭の問いや「次節で扱う」とした論点を回収しているか

### 観点5: 独自性と価値

公開する読み物（記事、スライド）だけに適用し、READMEや設計メモには適用しない。

次の両方を満たすときだけ「焼き直し」として要修正にする。(a) 一次情報に無い検証結果、落とし穴、比較、使い分けが1つも無い。(b) 本文を読まずに一次情報（MDNなど）の要約で同じ結論に届く。片方でも独自の要素があれば推奨以下にし、どこが既知情報の繰り返しで何を足せば独自になるかを具体的に示す。ニッチな題材を頭ごなしに否定しない。

### 観点6: 語り口と演出

文書を通した語りの一貫性と修辞の総量を見る。

- 例示は受動態ではなく行為者を主語にする。読者を「あなた」と呼ばず役割名で呼ぶ。導入した術語は最後まで通す。
- 修辞疑問、決め台詞、劇的な転回、対句を乱用しない。事故や危険を煽らない。意味が一つに決まらない比喩は平易な動詞にする。

### 観点7: 公開前チェック

- 空リンク（`[テキスト]()`）が無いか。外部リンクは任意で`curl -sI <url> | head -1`で到達を確かめる。
- バージョン番号、「Baseline 20XX」、日付などが公開時点で正しく、古びていないか。

## レポート

各指摘に場所（`file:line`）、該当箇所、なぜ問題か、修正案を書き、重要度ごとにまとめる。指摘ゼロの観点も「OK」と書いて、見た範囲を示す。

```markdown
## 文章レビュー: <ファイル名>

### 🔴 要修正

- `doc.md:88` 文体混在（ですます/である）→「〜です」に統一 ［該当: 「…注意すべきである。」］

### 🟡 推奨

- `doc.md:30-46` 「基本構文」より先に応用が来て理解の順が逆 → 節を入れ替える

### 🟢 任意

- `doc.md:60` 前節と同じ説明の言い換え → どちらかに寄せる

### 指摘なしの観点

- 観点1 日本語ルール、観点3 表記: OK
```

重要度の上限は次のとおり。好みの押し付けにならないよう、主観の観点は読者が明確に損をする箇所に絞る。

- 観点1〜3（客観的なルール違反）：要修正まで
- 観点4〜6（主観が入る）：推奨まで。例外として、観点4の論理矛盾と観点5の焼き直しは要修正にしてよい
